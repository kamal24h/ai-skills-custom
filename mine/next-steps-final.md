بدون اندازه‌گیری وضعیت فعلی، نمی‌توانیم بفهمیم Multi-Agent واقعاً کیفیت را بهتر کرده یا فقط پیچیدگی سیستم را افزایش داده است.

این نکته کاملاً درست است. من هم پیشنهاد می‌کنم Supervisor مالک Conversation State باشد و Agentها فقط Context مرتبط با مأموریتشان را دریافت کنند.

هـ) Reasoning Loop باید محدود باشد.

Agent نباید اختیار اجرای نامحدود Tool یا تکرار بی‌پایان داشته باشد. تعداد مراحل، زمان اجرا و تعداد فراخوانی ابزار باید محدود شوند.

## ۲. مواردی که به نظرم نیاز به اصلاح دارند

### ۲.۱. Query Understanding را با Intent Classifier یکی نکنیم

در ارزیابی، پیشنهاد شده `IntentClassifier` به `QueryUnderstanding` ارتقا پیدا کند. من با این تغییر به شکل فعلی موافق نیستم.

این دو مسئولیت متفاوت دارند:

| مؤلفه               | مسئولیت                                                          |
| ------------------- | ---------------------------------------------------------------- |
| Query Understanding | فهم معنایی درخواست، استخراج موجودیت‌ها، نرمال‌سازی و تشخیص وظایف |
| Intent Classifier   | انتخاب مسیر اجرایی براساس سیاست‌های سیستم                        |
| Supervisor          | برنامه‌ریزی، واگذاری و کنترل اجرای وظایف                         |

ما Query Understanding Agent را قبلاً به پروژه اضافه کرده‌ایم. بهتر است آن را حفظ کنیم و Intent Classifier را هم به‌عنوان یک لایه تصمیم‌گیری مستقل نگه داریم.

در واقع، Supervisor باید از خروجی این دو استفاده کند، نه اینکه تمام وظایف آن‌ها را مجدداً انجام دهد.

### ۲.۲. Evidence Verification را کاملاً به یک Agent نسپاریم

در سند، Evidence Verification به‌عنوان یک Agent پیشنهاد شده است؛ اما من این مسئولیت را به دو بخش تقسیم می‌کنم:

- Deterministic Evidence Validation: بررسی وجود منبع، ارتباط Source با پاسخ، تطابق شناسه‌ها، اعتبار داده‌ها و کامل بودن نتایج.
- Semantic Verification: بررسی اینکه آیا شواهد واقعاً از نتیجه‌گیری موردنظر پشتیبانی می‌کنند.

بخش اول باید قطعی و برنامه‌محور باشد. بخش دوم می‌تواند از LLM استفاده کند.

بنابراین بهتر است از ابتدا یک Agent دیگر با چرخه مستقل نسازیم؛ ابتدا یک Verification Layer طراحی کنیم و در صورت نیاز، قابلیت ارزیابی معنایی را به آن اضافه کنیم.

### ۲.۳. موازی‌سازی را صرفاً براساس نوع Agent انجام ندهیم

در فاز دوم، ارزیابی پیشنهاد داده که Retrieval Planning و ERP Tool Planning به‌صورت موازی اجرا شوند.

این تصمیم همیشه درست نیست.

مثلاً اگر ابتدا باید از مستندات بفهمیم معنای یک شاخص ERP چیست و سپس همان شاخص را از ERP استخراج کنیم، اجرای هم‌زمان این دو مرحله ممکن است باعث استفاده از پارامترهای اشتباه شود.

## ۴. یک نکته مهم: تعریف Task Contract

به نظرم این مهم‌ترین بخش طراحی فنی است و باید قبل از نوشتن Supervisor نهایی شود.

هر مأموریتی که به یک Agent می‌دهیم باید یک قرارداد مشخص داشته باشد. مثلاً:

```
class AgentTask:    task_id: str    parent_task_id: str | None    agent_type: str    objective: str    input_context: dict    expected_output_schema: str    dependencies: list[str]    max_tool_calls: int    timeout_seconds: int
```

و نتیجه اجرای Agent:

```
class AgentResult:    task_id: str    agent_type: str    status: str    result: dict    evidence: list[dict]    errors: list[dict]    execution_metrics: dict
```

این قرارداد باعث می‌شود Supervisor به نام و پیاده‌سازی داخلی Agentها وابسته نباشد. همچنین می‌توانیم Agentهای جدید را بدون تغییر اساسی در Coordinator ثبت کنیم.

البته در پیاده‌سازی واقعی، این دو مدل را با Pydantic، Enumهای محدود، Schemaهای خروجی مشخص و اعتبارسنجی سخت‌گیرانه تعریف می‌کنیم.

## ۵. تصمیم نهایی من

توصیه می‌کنم مسیر ترکیبی را انتخاب کنیم

از نظر من، ارزیابی پیوست در سه مورد از پیشنهاد قبلی من بهتر عمل کرده است:

1. Baseline را قبل از تغییر معماری قرار داده است.
2. اجرای موازی را به مرحله بعد از ایجاد Supervisor موکول کرده است.
3. توسعه Agentهای تخصصی را به نتایج واقعی پروژه وابسته کرده است.

اما من یک اصلاح مهم دارم: هدف فاز اول نباید صرفاً ساخت Supervisor و یک Inventory Agent باشد؛ باید یک زیرساخت قابل توسعه برای ثبت، اجرای کنترل‌شده و تبادل وظایف بین Agentها ایجاد شود. در غیر این صورت، ممکن است بعداً برای هر Agent جدید دوباره منطق اجرایی بنویسیم.

بنابراین پیشنهاد می‌کنم قبل از تغییر کد، این چهار سند فنی را نهایی کنیم:

1. `Multi-Agent Architecture`: معماری کلان و مرز مسئولیت‌ها.
2. `Agent Task Contract`: قرارداد ورودی و خروجی Agentها.
3. `Supervisor & Execution State`: منطق تصمیم‌گیری، Delegation و مدیریت وضعیت.
4. `Evaluation Dataset`: مجموعه تست و معیارهای اندازه‌گیری.

یک نکته درباره ترتیب کار: چون قبلاً Query Understanding Agent را پیاده‌سازی کرده‌ایم، لازم نیست آن را دوباره بسازیم یا حذف کنیم. ابتدا باید جایگاه دقیق آن را در معماری Supervisor مشخص کنیم.

من این معماری را برای دستیار ERP تو مناسب‌تر از یک Multi-Agent کاملاً آزاد می‌دانم: استقلال در حل مسئله، ولی کنترل مرکزی در اجرا و تصمیم‌های حساس.
