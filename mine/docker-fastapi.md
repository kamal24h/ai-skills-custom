برای بیلد پروژه FastAPI با Docker، حالت‌های مختلفی وجود دارد که هر کدام برای سناریوی خاصی (توسعه، پروداکشن، رفع باگ، به‌روزرسانی امنیتی) بهینه شده‌اند. در ادامه یک راهنمای جامع بر اساس ترکیب‌های مختلف **کش** و **نصب پیش‌نیازها** ارائه می‌شود.

### 🧱 پیش‌نیاز: ساختار بهینه Dockerfile برای FastAPI

قبل از دستورات، باید Dockerfile شما به گونه‌ای نوشته شده باشد که از کش به درستی استفاده کند. نکته کلیدی این است که فایل‌های وابستگی (`requirements.txt` یا `pyproject.toml`) را **قبل از** کپی کردن سورس‌کد کپی و نصب کنید تا با تغییر کد، دوباره وابستگی‌ها نصب نشوند .

```dockerfile
FROM python:3.11-slim

WORKDIR /app

# ۱. اول کپی کردن فقط فایل وابستگی‌ها (برای استفاده حداکثری از کش)
COPY requirements.txt .

# ۲. نصب پیش‌نیازها (این لایه تا زمانی که requirements.txt تغییر نکند، کش می‌شود)
RUN pip install --no-cache-dir -r requirements.txt

# ۳. در انتها کپی کردن سورس‌کد (این لایه با هر تغییر کد باطل می‌شود)
COPY . .

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 📊 حالت‌های مختلف بیلد

| حالت | دستور | چه زمانی استفاده شود؟ | رفتار کش | نصب پیش‌نیازها |
| :--- | :--- | :--- | :--- | :--- |
| **۱. بیلد عادی (با کش)** | `docker build -t my-fastapi .` | توسعه روزمره؛ وقتی فقط کد اپلیکیشن تغییر کرده است. | استفاده از کش لایه‌ها (سریع) | فقط اگر `requirements.txt` تغییر کرده باشد، دوباره نصب می‌شود. |
| **۲. بیلد بدون کش** | `docker build --no-cache -t my-fastapi .` | وقتی می‌خواهید مطمئن شوید آخرین نسخه پکیج‌ها نصب می‌شود یا کش خراب شده است. | نادیده گرفتن کامل کش (کند) | همه پیش‌نیازها از صفر نصب می‌شوند. |
| **۳. بیلد با به‌روزرسانی Base Image** | `docker build --pull -t my-fastapi .` | برای دریافت آخرین وصله‌های امنیتی سیستم‌عامل پایه (مثل `python:3.11-slim`). | کش استفاده می‌شود مگر اینکه Base Image تغییر کرده باشد. | فقط در صورت تغییر Base Image یا `requirements.txt` نصب می‌شوند. |
| **۴. بیلد کامل (بدون کش + به‌روزرسانی Base)** | `docker build --no-cache --pull -t my-fastapi .` | پروداکشن، رفع آسیب‌پذیری (CVE)، یا بیلدهای زمان‌بندی‌شده هفتگی. | نادیده گرفتن کامل کش و دریافت جدیدترین Base Image. | همه چیز از صفر و با آخرین نسخه‌ها نصب می‌شود. |
| **۵. بیلد چندمرحله‌ای (Multi-stage)** | `docker build -t my-fastapi .` (با Dockerfile چندمرحله‌ای) | پروداکشن؛ برای کاهش حجم ایمیج نهایی و جدا کردن ابزارهای بیلد از محیط اجرا. | مانند حالت ۱. | پیش‌نیازها در مرحله `builder` نصب و فقط نتایج به مرحله نهایی کپی می‌شوند . |
| **۶. بیلد با کش خارجی (CI/CD)** | `docker buildx build --cache-to type=registry,...` | در خط لوله CI/CD که کش محلی بین اجراها پایدار نمی‌ماند. | کش در یک رجیستری ذخیره و از آن بازیابی می‌شود . | بسته به تنظیمات کش، ممکن است نیازی به نصب مجدد نباشد. |

### 💡 نکات کلیدی برای هر حالت

**۱. بیلد عادی (با کش)**
این حالت پیش‌فرض است و برای توسعه روزمره عالی است. اگر فقط فایل `main.py` را تغییر داده‌اید، Docker لایه `COPY . .` را دوباره اجرا می‌کند اما لایه `RUN pip install` را از کش می‌خواند و بیلد در چند ثانیه تمام می‌شود .

**۲. بیلد بدون کش (`--no-cache`)**
زمانی که پکیج‌های سیستمی (مثل `apt-get`) را در Dockerfile دارید، کش می‌تواند شما را فریب دهد و وصله‌های امنیتی جدید را نادیده بگیرد. استفاده از `--no-cache` تضمین می‌کند که تمام دستورات `RUN` مجدداً اجرا شوند . توجه داشته باشید که این کار زمان بیلد را به شدت افزایش می‌دهد.

**۳. بیلد با `--pull`**
این گزینه فقط Base Image را از رجیستری دوباره دریافت می‌کند. اگر تیم امنیت به شما گفته است که یک آسیب‌پذیری در `python:3.11-slim` وصله شده است، کافی است از `--pull` استفاده کنید تا نسخه جدید دریافت شود، بدون اینکه کل لایه‌های اپلیکیشن بی‌جهت باطل شوند .

**۴. ترکیب `--no-cache --pull`**
این «سنگین‌ترین» حالت بیلد است و برای مواقعی است که می‌خواهید یک ایمیج کاملاً تازه و بدون هیچ اثری از کش قبلی بسازید (مثلاً برای انتشار در پروداکشن یا رفع یک باگ عجیب) .

**۵. بیلد چندمرحله‌ای (Multi-stage)**
در این روش، یک مرحله (`builder`) مسئول نصب پیش‌نیازها و بیلد است، و مرحله نهایی (`runtime`) فقط کد و پکیج‌های نصب‌شده را کپی می‌کند. این کار حجم ایمیج نهایی را به شدت کاهش می‌دهد (مثلاً از ~900MB به ~55MB) و سطح حمله را کم می‌کند .

**۶. کش خارجی برای CI/CD**
اگر از GitHub Actions یا GitLab CI استفاده می‌کنید، کش محلی Docker بین اجراها از بین می‌رود. در این صورت باید از `docker buildx` با `--cache-to` و `--cache-from` استفاده کنید تا کش را در یک رجیستری (مثل Docker Hub یا GHCR) ذخیره و بازیابی کنید .

### ⚠️ یک هشدار مهم

هرگز از ترفندهایی مثل اضافه کردن یک `ARG` با تاریخ تصادفی برای باطل کردن کش استفاده نکنید. این کار باعث می‌شود کش از آن نقطه به بعد **همیشه** باطل شود و دیگر نتوانید از مزیت سرعت کش در توسعه بهره‌مند شوید. همیشه از فلگ‌های صریح `--no-cache` یا `--pull` استفاده کنید .
