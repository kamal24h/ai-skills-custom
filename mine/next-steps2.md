# بررسی سند نقشه‌راه Multi-Agent پیشنهادی

سند پیوست، از نظر معماری **کیفی و حرفه‌ای** است و بسیاری از اشتباهات رایج مهاجرت به Multi-Agent را مرتکب نشده. اما قبل از تصمیم‌گیری، باید دقیق‌تر بررسی کنیم که کدام بخش‌ها واقعاً برای پروژه شما ارزش عملی دارند و کدام بخش‌ها فقط «معماری زیبا» هستند که در عمل زمان‌بر می‌شوند.

---

## ۱. نقاط قوت سند (بخش‌هایی که درست و ارزشمند هستند)

**۱.۱. جدا کردن «Multi-Agent برای درخواست‌های پیچیده» از «Workflow برای درخواست‌های ساده»**

نویسنده درست تشخیص داده که `SMALL_TALK`، `DOCUMENT_QUERY` ساده و `ERP_DATA_QUERY` ساده نباید از Multi-Agent عبور کنند. این جدول بخش ۱ درست است:

| نوع درخواست | معماری مناسب |
|---|---|
| سلام و احوال‌پرسی | مسیر مستقیم |
| سؤال از یک مستند | RAG Workflow |
| Multi-Agent | تحلیل چندمرحله‌ای |

این رویکرد **«Selective Multi-Agent»** است، نه «Everything Multi-Agent». بسیار خوب.

**۱.۲. تمرکز روی Supervisor مرکزی (Hierarchical) نه ارتباط آزاد Agentها**

این مهم‌ترین تصمیم درست سند است. تفویض آزاد Agentها به یکدیگر (agent-to-agent free chat) در سیستم ERP که عملیات نوشتن دارد، ریسک بالایی دارد. Supervisor با **Task Contract** و خروجی ساختاریافته، خطا را محدود می‌کند.

**۱.۳. تمرکز روی «آنچه نباید به Agent سپرده شود» (بخش ۶)**

نویسنده به‌درستی اشاره می‌کند که احراز هویت، کنترل دسترسی، اعتبارسنجی پارامتر، و تأیید عملیات نوشتن باید **خارج از Agent** و در لایه قطعی برنامه باقی بمانند. این با معماری فعلی شما هم‌راستاست (approval_store، validate_tool_arguments، guardrails).

**۱.۴. حفظ زیرساخت فعلی (بخش ۷)**

سند صراحتاً می‌گوید «پروژه موجود را از ابتدا بازنویسی نمی‌کنم». زیرساخت RAG، MCP، Redis، Postgres، Approval، Guardrails همه حفظ می‌شوند. این تصمیم عملی و کم‌ریسک است.

**۱.۵. تاکید روی Context Isolation**

هر Agent فقط اطلاعات مربوط به مأموریت خودش را دریافت می‌کند. این از «انفجار Context» جلوگیری می‌کند (مشکلی که در پروژه‌های Multi-Agent شایع است) و هزینه توکن را هم کنترل می‌کند.

**۱.۶. تعریف ۸ ویژگی برای Agent واقعی**

در بخش ۴، ۸ ویژگی (Identity، System Prompt، Reasoning Loop، Tools، Context، State، Structured Output، Failure Handling) تعریف شده که یک Agent را از یک Node تمیز می‌دهد. این تعریف دقیق و قابل دفاع است.

**۱.۷. تصدیق اینکه Query Understanding Agent فعلی «Agent واقعی نیست»**

نویسنده به‌درستی گفته که Query Understanding فعلی یک مرحله پردازش است، نه Agent مستقل. این صداقت فنی خوبی است—اما در عمل نشان می‌دهد که معماری سند، Query Understanding را به یک role خاص در Supervisor تبدیل می‌کند، نه Agent مستقل.

## ۲. نقاط ضعف و ریسک‌های سند (بخش‌هایی که باید محتاط بود)

**۲.۱. هفت فاز پیشنهادی بیش از حد بلندپروازانه است**

سند در بخش ۷ یک roadmap هفت‌فازی پیشنهاد می‌دهد:

| فاز | کار |
|---|---|
| ۱ | تبدیل Coordinator به Supervisor |
| ۲ | Agent Runtime مشترک |
| ۳ | Document Research و ERP Domain Agent |
| ۴ | Parallel Execution |
| ۵ | Evidence Verification و Response Agent |
| ۶ | حافظه، مدیریت خطا، HITL |
| ۷ | ارزیابی و بهینه‌سازی |

**مشکل**: فازهای ۱ و ۲ به تنهایی چند هفته کار هستند و بدون خروجی قابل استفاده به کاربر. اگر تیم شما ۱-۲ نفر باشد، این roadmap ۳-۶ ماه طول می‌کشد تا اولین نسخه قابل استفاده برسد. این ریسک بزرگی است.

**پیشنهاد**: فازبندی باید **کوچک‌تر و نتیجه‌محورتر** باشد. مثلاً:
- فاز ۱ (۲-۳ هفته): Supervisor + Task Contract + یک Domain Agent (فقط Inventory یا Sales)
- فاز ۲ (۲-۳ هفته): موازی‌سازی فقط بین دو Agent که واقعاً مستقلند
- فاز ۳ (۲-۴ هفته): Evidence Verification + Synthesis

**۲.۲. ساختار پوشه پیشنهادی (بخش ۷) بیش از حد بزرگ است**

```
agents/
├── supervisor/
├── planning/
├── query_understanding/
├── domain/
│   ├── production/
│   ├── inventory/
│   ├── sales/
│   └── finance/
├── document_research/
├── data_analysis/
├── evidence_verification/
└── response/
```

این ساختار برای تیم ۵-۱۰ نفره طراحی شده، نه برای یک پروژه که در حال حاضر `workflow.py` دارد. **پیشنهاد**: به‌جای این ساختار، ابتدا فقط `supervisor/` و `domain/` را بسازید و Domain Agentها را در یک فایل جمع کنید. وقتی تعداد واقعاً زیاد شد، split کنید.

**۲.۳. «حافظه مشترک» (بخش ۸) در فاز اول خطرناک است**

سند می‌گوید همه Agentها از «حافظه مشترک» استفاده کنند. اگر منظور از حافظه مشترک، conversation history است که به همه Agentها تزریق شود، این همان «Context Explosion» است که سند در بخش ۱.۵ سعی در جلوگیری از آن داشت. **پیشنهاد**: هر Agent حافظه خودش را داشته باشد، و Supervisor فقط خلاصه‌های ساختاریافته را بین Agentها جابجا کند.

**۲.۴. «مدل‌های مختلف» (بخش ۸، مدیریت مدل)**

سند پیشنهاد می‌کند Agentهای سبک از Local LLM و Agentهای سنگین از OpenAI استفاده کنند. **این تصمیم در شرایط فعلی شما ریسکی است**، چون:
- `openai_enabled` فعلی شما `false` است.
- Guardrails فعلی شما `force_local` برای درخواست‌های enterprise/PII اعمال می‌کند (به `assess_input` در `guardrails.py` نگاه کنید). یعنی حتی اگر OpenAI را فعال کنید، برای اکثر سؤالات ERP به Local برمی‌گردد.
- هزینه OpenAI برای Agentهای متعدد می‌تواند چند برابر شود.

**پیشنهاد**: در فاز اول، همه Agentها از همان Local Qwen استفاده کنند. فقط اگر بعد از اندازه‌گیری متوجه شدید یک Agent خاص (مثلاً Response Synthesizer) با Local خروجی ضعیف دارد، آن یکی را به OpenAI منتقل کنید. **تصمیم مدل را به فاز ۷ (ارزیابی) موکول کنید، نه فاز ۱**.

**۲.۵. «Reasoning Loop» برای Agentها (بخش ۴، ویژگی ۳)**

سند برای هر Agent یک «Reasoning Loop» پیشنهاد می‌کند. این عبارت می‌تواند خطرناک باشد: اگر Agent بتواند در حلقه تصمیم بگیرد «دوباره ابزار صدا بزنم»، می‌تواند به حلقه بی‌پایان بیفتد یا فراخوانی‌های زائد انجام دهد. **پیشنهاد**: در فاز اول، Agentها **بدون** reasoning loop باشند (یک ورودی، چند tool call محدود، یک خروجی). Reasoning loop را فقط در صورتی اضافه کنید که یک use case خاص نیاز داشته باشد و با `max_iterations` و timeout کنترل کنید.

**۲.۶. نبود «ارزیابی کمی قبل از شروع»**

سند در فاز ۷ به «ارزیابی» اشاره می‌کند، اما ارزیابی باید **قبل از فاز ۱** انجام شود. بدون baseline، بعد از مهاجرت نمی‌دانید بهتر شده یا بدتر.

## ۳. مقایسه سند با پیشنهاد قبلی من

| موضوع | پیشنهاد قبلی من | سند پیوست |
|---|---|---|
| نوع معماری | Supervisor + Parallel Sub-Agents (سبک) | Hierarchical Multi-Agent (سنگین‌تر) |
| تعداد Agentها | ۴ Agent ضروری + Query Understanding | ۷ نوع Agent + چند Domain Agent |
| فازبندی | ۴ فاز (بدون فاز ۰) | ۷ فاز |
| مدل LLM | همه از Local | ترکیب Local و OpenAI |
| موازی‌سازی | فقط بین دو Planning | موازی‌سازی در Execution (عمومی) |
| ساختار پوشه | ساده‌تر | مفصل‌تر |
| Domain Agentها | ندارد | دارد (Production, Inventory, ...) |

**سند پیوست مزیت‌هایی دارد**: Domain Agentها برای ERP منطقی هستند و در بلندمدت مفیدند. اما **پیشنهاد قبلی من به واقعیت پروژه فعلی نزدیک‌تر است** و ریسک کمتری دارد.

## ۴. توصیه من: مسیر ترکیبی

بهترین مسیر، **ترکیب نقاط قوت هر دو** است. این چیزی است که پیشنهاد می‌کنم:

### فاز 0 (۱-۲ روز): Baseline و تصمیم‌گیری داده‌محور
- ۵۰ سؤال تستی بسازید (شامل سه‌گانه فاکتور فروش).
- دقت Intent، دقت مسیر، False MCP Rate، False RAG Rate را اندازه بگیرید.
- **تصمیم بگیرید**: آیا مشکل اصلی «تشخیص قصد» است یا «پردازش تخصصی»؟ اگر اولی، Multi-Agent کمکی نمی‌کند.

### فاز 1 (۲-۳ هفته): Supervisor + Query Understanding + یک Domain Agent
- `IntentClassifier` فعلی را به `QueryUnderstanding` ارتقا دهید (extract entities + normalize + detect intent).
- یک `SupervisorAgent` ساده بسازید که فقط تصمیم می‌گیرد:
  - مسیر ساده (local_llm، local_rag، local_mcp ساده) → همان workflow فعلی
  - مسیر پیچیده (multi-step) → وارد فاز Supervisor
- **یک** Domain Agent (مثلاً Inventory) بسازید.
- **موازی‌سازی در این فاز نکنید**.

**خروجی فاز ۱**: درخواست‌های ساده همان‌طور که هستند کار می‌کنند؛ درخواست‌های پیچیده با Supervisor + یک Domain Agent اجرا می‌شوند.

### فاز 2 (۲-۳ هفته): موازی‌سازی واقعی
- `Retrieval Planning` و `ERP Tool Planning` را به عنوان دو node موازی در Supervisor فعال کنید.
- فقط بین Domain Agentهایی که واقعاً مستقلند (مثلاً Inventory + Sales) موازی‌سازی کنید.
- **معیار سنجش**: تأخیر درخواست‌های MIXED_QUERY چقدر کاهش یافت؟ دقت کاهش نیافت؟

### فاز 3 (۲-۴ هفته): Evidence Verification + Response Synthesizer
- `EvidenceVerificationAgent` را اضافه کنید (با تأیید قطعی، نه LLM).
- `ResponseSynthesizer` را جایگزین `planning_node` فعلی کنید.
- فقط پس از این فاز، ارزیابی مجدد با همان ۵۰ سؤال انجام دهید.

### فاز 4 (اختیاری، در صورت مفید بودن): Domain Agentهای بیشتر
- اگر فازهای ۱-۳ واقعاً بهبود دادند، Agentهای بعدی (Sales، Purchase، Finance، Production) را یکی‌یکی اضافه کنید.
- **تصمیم مدل** (Local vs OpenAI) را در این فاز بگیرید.
- حافظه مستقل برای هر Agent را در این فاز بررسی کنید.

## ۵. یک جمله برای تصمیم‌گیری

**سند پیوست از نظر معماری حرفه‌ای است، اما ۷ فاز و ۷ نوع Agent برای پروژه فعلی بیش از حد بلندپروازانه است و ریسک دارد که نیمه‌کاره رها شود.** مسیر بهینه: **فاز ۰ را انجام دهید تا داده داشته باشید، سپس فاز ۱ و ۲ را با ۳ Agent (Supervisor + Query Understanding + یک Domain Agent) پیاده کنید**. اگر این ۲ فاز واقعاً بهبود دادند (در سرعت یا کیفیت پاسخ‌های پیچیده)، فازهای ۳ و ۴ را ادامه دهید. اگر نه، در همان معماری فعلی بمانید—که از نظر معماری هم قابل دفاع است.

پیشنهاد مشخص: **پیش از اجرای فاز ۱، یک جلسه طراحی ۲ ساعته بگذارید تا Task Contract، State مشترک و Decoupling مرز مسئولیت‌ها را مکتوب کنید.** این سند، ماده خام خوبی برای آن جلسه است.
